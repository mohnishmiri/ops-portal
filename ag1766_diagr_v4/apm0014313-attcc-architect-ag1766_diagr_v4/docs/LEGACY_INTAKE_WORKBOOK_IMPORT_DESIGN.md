# Legacy Completed Intake Workbook Import — Design

**Status:** Proposed for implementation review  
**Date:** 2026-09-11  
**Trigger:** `App Data Capture_intake_1.xlsx` was uploaded through the source-document lane, parsed as evidence, and quarantined because no supported source identity sheet was present.

## 1. Problem

The application currently has two workbook lanes:

1. **Source documents** such as UAQ and Interface Tracking. These are external evidence and must identify the application before their candidates can be accepted.
2. **Canonical intake form** generated by this application. It carries internal application, intake, catalog, question, and row-version identifiers and can be safely round-tripped.

The legacy App Data Capture workbook is neither. It is a completed questionnaire organized into `App`, `iTAP`, `WaveUtil`, `Infra`, `Database`, `TSS`, and `Provisioning` sheets. The existing structured adapters can extract parts of it, but the evidence workflow only recognizes authoritative identity from `UAQ` and `Migrating App Data`. Treating it as ordinary source evidence therefore produces a misleading quarantine.

The product needs a third explicit lane for a **legacy completed intake workbook**. This lane may use Correlation ID, MOTS ID, or iTAP ID to resolve an application, but external identifiers must never silently select an intake, attach a new identifier, or overwrite a concurrently changed answer.

## 2. Accepted decisions

1. **Target intake:** after deterministic application matching, the user chooses an eligible intake.
2. **Identifier precedence:** Correlation ID is authoritative when present. MOTS and iTAP are fallbacks only when Correlation is absent.
3. **Unknown identifier:** reject the import before candidates are created. Identity enrollment remains a separate application-administration action.
4. **Concurrency:** capture each target answer's baseline revision at import time and block acceptance if that answer changed before review.

## 3. Product invariants

- Importers create candidates, never approved answers.
- External IDs identify applications; only internal UUIDs identify application and intake records.
- Never infer identity from application name, acronym, filename, worksheet name, or upload URL.
- Never infer `No` or another answer from blank/missing cells.
- Never silently select an intake when more than one eligible intake exists.
- Never silently resolve contradictory identifiers.
- Preserve every supplied identifier, its type, raw value, normalized value, and source locator.
- A matching identifier authorizes proposal creation only; candidate acceptance remains an explicit reviewer action.
- Existing canonical intake-form and source-document lanes remain strict and unchanged.

## 4. Terminology and lane model

### Lane 1 — Source documents

Existing evidence path. UAQ, Interface Tracking, and other external source exports. Identity is source-derived and candidates retain evidence provenance.

### Lane 2 — Canonical intake form

Existing `GAP_WORKBOOK_REIMPORT_V1` path. The form is generated for a specific internal application and intake and carries row-version tokens.

### Lane 3 — Legacy completed intake workbook

New `APP_DATA_CAPTURE_LEGACY_V1` path. It accepts the seven-sheet App Data Capture contract, extracts external identity, resolves exactly one application, asks the user to choose an intake, and creates reviewable candidates with baseline answer versions.

The legacy file remains evidence and should be stored through `EvidenceService` for hash, filename, media type, and immutable provenance, but it is processed by a separate orchestration service rather than by the generic source-document workflow.

## 5. Identity contract

### 5.1 Supported identifier types

Canonical application identifier codes remain:

- `CORRELATION`
- `MOTS`
- `ITAP`

The legacy reader must map recognized workbook labels to those codes through an explicit versioned alias registry. It must not use fuzzy matching.

Initial alias examples are design inputs, not final mappings:

| Canonical type | Candidate labels |
|---|---|
| CORRELATION | Application correlation ID, Correlation ID |
| MOTS | MOTS ID, MOTS application ID |
| ITAP | iTAP ID, iTAP application ID |

Before implementation, labels and cell layouts must be confirmed against synthetic fixtures modeled on the contract. Private workbooks must not become test fixtures.

### 5.2 Precedence algorithm

1. Parse all recognized identity fields from all allowed identity-bearing sheets.
2. Normalize with the existing alphanumeric, case-insensitive policy.
3. Within each type:
   - no nonblank values: type is absent;
   - one distinct normalized value: type is usable;
   - multiple distinct normalized values: `SOURCE_ID_CONFLICT`, reject.
4. If Correlation is present, resolve by `CORRELATION` only.
5. Otherwise resolve by MOTS if present.
6. Otherwise resolve by iTAP if present.
7. If no supported identifier is present: `APPLICATION_ID_MISSING`, reject.
8. If the selected identifier matches no application: `APPLICATION_MISMATCH`, reject.
9. If it matches more than one application: `AMBIGUOUS_APPLICATION_MATCH`, reject.
10. If lower-priority supplied identifiers resolve to a different application than the selected identifier, reject as `SOURCE_ID_CONFLICT` rather than ignoring the contradiction.
11. If all supplied identifiers are consistent, return `APPLICATION_MATCHED` and the matched internal application ID.

### 5.3 Why precedence is not silent disagreement

“Correlation preferred” means Correlation chooses the lookup key when available. It does not permit a matching Correlation ID and a conflicting MOTS/iTAP ID to proceed. All supplied strong IDs must be consistent with the selected application.

### 5.4 Application selected in the URL

The lane should begin outside a specific intake because intake selection follows application resolution. It may be exposed from the application workspace or a global import page. If launched from an application workspace, the resolved application must equal that application; mismatch is rejected.

## 6. Intake selection

After identity resolution, show the matched application and its eligible intakes.

An eligible intake is:

- owned by the matched application;
- not frozen or otherwise immutable;
- pinned to a published catalog supported by the legacy mapping version;
- accessible to the current actor.

Rules:

- zero eligible intakes: stop and offer navigation to create an intake;
- one eligible intake: preselect it, but require an explicit Continue action;
- multiple eligible intakes: require selection; show state, catalog version, created/updated time, and current completeness;
- never create an intake implicitly;
- repeat submission is idempotent by evidence hash, contract version, parser version, and chosen intake.

## 7. Proposed user journey

### Step 1 — Upload

Add a third card on the Sources page or application workspace:

**Legacy completed intake workbook**  
“Use this for the older seven-tab App Data Capture workbook. The application is verified from Correlation, MOTS, or iTAP ID before any proposals are created.”

Upload performs safe workbook inspection and identity extraction only. No candidates are created yet.

### Step 2 — Identity result

Show:

- workbook filename and hash;
- detected contract and sheet summary;
- every detected identifier with type, raw value, normalized value, and source locator;
- identifier used for matching;
- matched application name and internal ID;
- warnings for missing optional IDs;
- blocking error for missing, unknown, ambiguous, or conflicting identity.

Do not offer a manual override on this screen.

### Step 3 — Choose intake

When identity is matched, display eligible intakes for that application. Require selection and confirmation.

### Step 4 — Parse and stage

Process all supported sheets using deterministic adapters and a versioned mapping. Persist an import run, sheet results, findings, and candidates. Stamp every candidate with:

- matched application ID;
- selected intake ID;
- evidence item ID and import run ID;
- contract/parser/mapping versions;
- source sheet, row, cell or label;
- raw and normalized values;
- application scope or narrower register scope;
- baseline answer revision/version for QUESTION targets.

### Step 5 — Review

Reuse the existing candidate coverage screen, with a lane badge of **Legacy intake form** and a visible identity summary. The review shows current answer versus proposed answer and findings.

### Step 6 — Accept

At acceptance time:

1. reload the current target answer;
2. compare its current revision/version with the candidate's baseline;
3. if unchanged, validate the candidate against the current catalog response type and question vocabulary, then write the new answer revision and evidence link atomically;
4. if changed, keep the candidate proposed/deferred and return `ANSWER_CHANGED_SINCE_IMPORT`; show current and proposed values and require a new reviewer decision or reimport.

Bulk acceptance must evaluate each candidate independently and report accepted, stale, invalid, and ineligible counts. It must not hide partial outcomes.

## 8. Import states and decisions

Recommended import states:

- `UPLOADED` — evidence stored, not inspected;
- `IDENTITY_REJECTED` — missing/unknown/ambiguous/conflicting identifier;
- `AWAITING_INTAKE_SELECTION` — application matched;
- `PROCESSING` — deterministic parsing in progress;
- `COMPLETED` — candidates/findings persisted;
- `FAILED` — technical failure;
- `SUPERSEDED` — optional future state for explicit replacement.

Existing identity decision codes can be reused:

- `APPLICATION_MATCHED`
- `APPLICATION_ID_MISSING`
- `APPLICATION_MISMATCH`
- `AMBIGUOUS_APPLICATION_MATCH`
- `SOURCE_ID_CONFLICT`

The UI should distinguish a business rejection from a technical failure.

## 9. Data model

### 9.1 Import run

Extend `import_runs` rather than create a parallel import system. Recommended fields:

- `import_lane` (`SOURCE_DOCUMENT`, `CANONICAL_INTAKE_FORM`, `LEGACY_INTAKE_FORM`);
- `matched_identifier_type`;
- existing `source_identity_raw` and `source_identity_normalized` for the chosen lookup identity;
- existing `identity_detail` for all extracted identifiers, locators, precedence, and match evidence;
- `mapping_version` if not represented by parser/contract version;
- nullable `intake_id` while awaiting selection, populated before candidate creation.

If changing `application_id` to nullable during pre-resolution would weaken current invariants, use a short-lived signed upload token or a dedicated staging record until the application is matched. Prefer a database staging record for restart-safe/auditable operation, but keep it minimal.

### 9.2 Candidate baseline concurrency

Add one of the following to candidates:

Preferred:

- `base_answer_revision` nullable integer for QUESTION candidates;
- `base_answer_present` or use `0` to represent no answer.

Alternative:

- store the baseline in `validation_json`, which avoids DDL but makes an essential concurrency contract less explicit and less queryable.

The preferred explicit column is recommended. It is an acceptance invariant, not incidental validation metadata.

### 9.3 Identifier uniqueness

Current application identifiers are unique by `(identifier_type, normalized_value)`. Identity resolution must query typed identifiers and must never compare values across types.

## 10. Service boundaries

### New pure import components

- `LegacyIntakeWorkbookInspector`: recognizes the exact seven-sheet contract and safe workbook structure.
- `LegacyIntakeIdentityExtractor`: extracts typed IDs with deterministic locators.
- `resolve_application_identity`: generalized typed resolver supporting precedence and cross-ID consistency.
- `LegacyIntakeMapping`: versioned mapping from legacy fields/questions to catalog question codes/register fields.

### New orchestration service

`LegacyIntakeImportService`:

- stores/loads evidence through existing ports;
- inspects contract;
- resolves identity;
- lists eligible intakes through application queries;
- after explicit selection, invokes deterministic adapters/mapping;
- persists import run, results, findings, candidates atomically.

### Existing services reused

- `EvidenceService` and `FilesystemStore` for immutable file storage;
- `ApplicationRepository` for typed identifiers;
- `ImportRepository` and `CandidateRepository` for audit records;
- response registry and catalog options for candidate validation;
- candidate acceptance service for answer revision and evidence-link writes, extended with baseline conflict checking.

Routes remain thin and perform no SQL.

## 11. Route design

Suggested routes:

- `POST /applications/{app_id}/legacy-intake/upload`
  - stores workbook, inspects identity, returns identity result;
- `GET /applications/{app_id}/legacy-intake/{run_id}/target`
  - shows identity verdict and eligible intakes;
- `POST /applications/{app_id}/legacy-intake/{run_id}/target`
  - CSRF-protected explicit intake selection and processing;
- existing import detail and coverage routes
  - reused after candidates are persisted.

A global upload route could be added later. Application-scoped upload is safer for the first slice because it provides an expected application that must agree with the workbook.

## 12. Mapping policy

The existing sheet adapters do not guarantee that every emitted key maps to a catalog question. The observed `PROVISIONING-UNKNOWN` candidates prove that extraction without a reviewed mapping is insufficient.

Implementation must include a reviewed, versioned legacy mapping artifact. For each supported field it defines:

- source sheet and exact label/header;
- target kind and key;
- response type/schema version;
- deterministic normalization;
- scope derivation;
- allowed-value mapping;
- blank behavior;
- provenance locator.

Unknown fields become findings, not accept-capable QUESTION candidates. A target key such as `PROVISIONING-UNKNOWN` must never be reviewable as a canonical answer.

## 13. Validation and error behavior

Blocking before candidate creation:

- unsafe or malformed XLSX;
- wrong workbook contract;
- missing identifier;
- identifier not registered;
- ambiguous typed identifier;
- contradictory supplied identifiers;
- selected intake belongs to another application;
- selected intake is frozen/ineligible;
- unsupported catalog/mapping version.

Nonblocking findings:

- blank optional source value;
- unmapped legacy field;
- invalid candidate value;
- duplicate identical source values;
- proposal for an already-answered question (shown as current versus proposed).

Blocking at acceptance:

- answer changed since import;
- candidate value fails response schema or catalog vocabulary;
- candidate/application/intake mismatch;
- import identity no longer resolves consistently;
- frozen intake or insufficient capability.

No raw exception should reach the user; all expected failures return actionable messages.

## 14. Security and audit

- Use the existing safe XLSX inspection limits before openpyxl parsing.
- Enforce file size, decompression, formula/macro, and path safety controls.
- CSRF-protect upload target confirmation and candidate decisions.
- Authorize application and intake access on every route.
- Do not log workbook contents or identifier values at INFO level.
- Audit upload, identity decision, selected intake, processing result, acceptance conflict, and final decisions.
- Preserve evidence hash and immutable source locators.
- Do not attach unknown IDs during import.

## 15. Test strategy

All fixtures must be synthetic.

### Unit tests

Identity extraction:

- Correlation only;
- MOTS fallback when Correlation absent;
- iTAP fallback when both higher-priority IDs absent;
- blank IDs ignored;
- duplicate identical IDs collapse;
- conflicting values of one type reject;
- Correlation match plus conflicting MOTS rejects;
- exact aliases only, no fuzzy matching;
- raw and normalized values plus locators preserved.

Identity resolution:

- unique typed match;
- unknown ID;
- ambiguous ID;
- selected application mismatch;
- values identical across different types do not cross-match.

Mapping:

- each reviewed source field maps to the expected target and shape;
- blank is not converted to `No`;
- unknown field creates a finding, not an accept-capable candidate;
- values outside catalog vocabulary are findings/ineligible.

Concurrency:

- no existing answer baseline;
- existing answer revision baseline;
- unchanged acceptance succeeds;
- answer changed after import blocks acceptance;
- unrelated answer change does not block;
- bulk action reports mixed outcomes.

### Repository/contract tests

Run against SQLite and Oracle:

- new migration upgrade;
- Oracle-safe identifiers;
- import lane and identity detail round trip;
- baseline revision round trip;
- idempotency key behavior;
- transaction rollback leaves no partial candidates.

### Web integration tests

- third lane is clearly labeled;
- legacy workbook in source lane gets a directional message;
- wrong contract in legacy lane is rejected;
- identity summary is rendered;
- unknown ID produces no candidates;
- matched app shows only eligible intakes;
- explicit intake selection is required;
- selected intake mismatch is rejected;
- successful processing lands on existing review page;
- stale proposal displays conflict and is not accepted;
- CSRF and resource authorization.

### Browser journey

1. create an application with Correlation, MOTS, and iTAP IDs;
2. create two eligible intakes;
3. upload a synthetic legacy workbook with matching Correlation ID;
4. verify matched application and choose the second intake;
5. process and review proposals;
6. modify one answer through the questionnaire after import;
7. bulk accept;
8. verify unchanged proposal accepted, changed proposal blocked;
9. verify provenance and current questionnaire values;
10. repeat with Correlation absent and MOTS fallback.

### Regression

- canonical intake-form journey remains unchanged;
- UAQ/source-document journey remains unchanged;
- identity quarantine remains strict;
- full SQLite suite;
- focused Oracle contracts and browser journey;
- mypy and ruff.

## 17. Acceptance criteria

The feature is complete when:

1. A legacy seven-sheet workbook has its own unmistakable upload lane.
2. Correlation is used first; MOTS then iTAP are deterministic fallbacks.
3. Every supplied strong ID is consistent with the same application.
4. Unknown, missing, ambiguous, or conflicting identity creates no candidates.
5. The reviewer explicitly chooses an eligible intake after application matching.
6. Supported values become scoped, provenance-bearing proposals only.
7. Unknown legacy fields never become accept-capable `*-UNKNOWN` question candidates.
8. Candidate acceptance revalidates schema/vocabulary and blocks stale-answer overwrites.
9. Bulk review reports partial outcomes without hiding conflicts.
10. Canonical form and source-evidence lanes retain their current strict behavior.
11. The feature passes synthetic SQLite and Oracle tests plus a browser journey.

## 18. Open mapping questions before L04

These require product/data-owner review rather than developer inference:

- exact source labels/cells for Correlation, MOTS, and iTAP IDs;
- which of the seven sheets are authoritative for each ID;
- precedence when the same type appears on multiple sheets;
- reviewed mapping of legacy App questions to current catalog question codes;
- whether iTAP, TSS, Provisioning, and WaveUtil content maps to questionnaire answers, registers, or findings;
- supported legacy workbook versions and how they are detected;
- whether already-imported quarantined runs can be reclassified, or only newly uploaded files use the lane.
