Topology-Diagram Generation Assessment

1. Executive Summary

The application can upload, populate, store, review, and download draw.io topology artifacts. However, the HTTP workflow currently uses the legacy label-only generator, not the newer governed topology runner.

The principal gaps are:

  1. Database interface records are not consumed. adapter.py explicitly returns "interfaces": [].
  2. “Official” generation pins snapshot metadata but still reads live answers; _generate_diagram() ignores its snapshot argument and queries current database state in topology_generation.py.
  3. Interface data is absent from immutable snapshots and governed preview captures.
  4. Existing renderers cannot yet create repeated interface nodes and styled edges required by the guide.
  5. Migration 0020 defines governed topology tables and columns that are missing from the corresponding ORM models and repository.
  6. Focused topology test collection currently fails with eight import errors, so broad regression protection is not operational.

The recommended solution is to extend the governed immutable-input pipeline with a typed interface projection and a versioned structural rendering profile. Database queries should remain simple SQLAlchemy repository operations; filtering, normalization, grouping, conflict detection, layout, and styling should be pure Python.

No handoff documents were reviewed.

  • Reads: application, identifiers, current answer revisions, optional snapshot metadata, and base diagram metadata.

  • Rendering: fill.py replaces configured labels while verifying geometry and structure remain unchanged.
  • Storage: diagram and HTML report bytes are placed in content-addressed filesystem storage; metadata is stored in gen_artifacts.

4. Guide and Workbook Findings

The DOCX contained 18 editable rule paragraphs and 11 embedded PNG diagrams. Windows OCR recovered section labels, but some image text was imperfect and the actual arrow colors were not recoverable.

Verified guide rules:

  • AT&T Internal Interfaces: locations in column G matching Midrange, Hybrid, Private, Conexus, or OnPrem; inbound records; group by columns N and R.
  • AWS Tier 1 / PaaS: column G matching AWS; inbound records; group by N and R.
  • Azure: column G matching Azure; inbound records; group by N and R.
  • Data-flow legend: includes a “Multiple Protocols” category, but its visual color is unreadable.
  • Standard sections: CI/CD tooling, DNS private hosted zones, AWS Home Region/connectivity, AWS Tier 2/control plane, Conexus/GPN, and Windows-only email.
  • Application-derived box: appears to include NAS, EC2, network, and storage details, but exact field mappings are image-only and OCR is insufficient.
  • Images suggest interface name/identifier labels and IN/OUT line treatment, which conflicts with the editable text’s inbound-only rule.

Workbook structure:

  • Visible sheets: App, Interface, iTAP, WaveUtil, Infra, Database, TSS, Provisioning.
  • Authoritative interface table: Table1, range A1:AG69, 33 columns and 68 data rows.
  • No formulas, validation lists, hidden rows/columns, or merged cells occur in the Interface table.
  • Direct guide mappings: G = system location, I = traffic direction, N = target protocol, R = future port.
  • Sanitized quality metrics: 61 rows have an interface ID; 9 repeated-ID groups cover 22 rows; 4 exact-duplicate groups cover 16 rows; 27 rows are inbound, 20 outbound, and 21 blank; 46 future ports are valid integers and 22 are blank.
  • The workbook supplies no explicit null, conflict, sorting, pagination, or fallback policy.

6. SQLite and Oracle Assessment

interfaces uses portable UUID/timestamp conventions and ordinary String/Text columns. Queries use SQLAlchemy expressions, so no database-specific topology business logic is necessary.

Risks:

  • Oracle converts empty strings to NULL; normalization must occur before mapping.
  • list_records_for_application() has no deterministic ordering.
  • Exact duplicate detection scans active rows in Python.
  • No (application_id, state) index is defined, which may matter for large registers.
  • Interface rows are mutable application-level state and not intake-scoped.
  • Snapshot/capture consistency cannot be proven unless interface rows and row versions are captured atomically.
  • Migration 0020, ORM models, and repository APIs are currently inconsistent.

Basic interface retrieval requires no schema change. Authoritative generation requires a versioned canonical contract containing interfaces; an index and capture-fencing migration may also be justified after measurements.

8. Proposed Target Architecture

flowchart LR
    API[Topology API] --> App[Generation application service]
    App --> Capture[Immutable capture service]
    Capture --> IR[Interface repository port]
    Capture --> AR[Answers/resources repositories]
    Capture --> Model[Canonical topology input]
    Model --> Rules[Pure interface mapping policy]
    Rules --> Projection[Normalized topology projection]
    Projection --> Renderer[Versioned structural renderer]
    Renderer --> Verify[Structural verification]
    Verify --> Store[Artifact store]
    Verify --> Audit[Run, manifest, issues, audit]

Introduce a typed TopologyInterface containing only approved fields, normalized location/direction/protocol/port, source record ID, row version, and provenance. Repository reads should return active rows in deterministic order.

A pure mapping policy should:

  1. Normalize case and approved aliases.
  2. Preserve unknown values as issues rather than infer classifications.
  3. Filter inbound only if that rule is approved.
  4. Group by section, normalized target protocol, and normalized future port.
  5. Preserve distinct rows sharing an interface ID.
  6. Flag conflicting rows instead of selecting one silently.
  7. Produce stable ordering and deterministic generated cell IDs.

Extend a versioned structural profile with prototype nodes, edge prototypes, style keys, spacing, capacity, pagination, and a reviewed protocol/port-to-style map. Include interface-set hash, profile hash, base hash, selection hash, and policy hashes in semantic input identity.

10. Regression-Prevention Strategy

  • Establish a green baseline before implementation; this is currently blocked by collection errors.
  • Use synthetic fixtures only.
  • Unit-test every normalization, classification, grouping, ordering, duplicate, conflict, and style rule.
  • Run repository contracts on SQLite and an explicitly authorized disposable Oracle schema.
  • Compare generated draw.io XML structurally: cells, edges, parents, styles, geometry, and untouched template content.
  • Retain golden artifacts only for reviewed synthetic profiles.
  • Repeat identical inputs and assert byte-identical diagram, report, manifest, and hashes.
  • Test zero, one, many, duplicate, conflicting, null, invalid-port, unknown-location, inbound/outbound, and overflow cases.
  • Test existing label-only workflows unchanged.
  • Measure representative registers at 10, 100, 1,000, and 5,000 rows.
  • Manually review section placement, legibility, edge direction, legend agreement, page overflow, and sensitive-data exclusion.

12. Risks, Assumptions, and Open Questions

  1. What exact colors/styles correspond to each protocol/port group?
  2. Are outbound interfaces omitted, rendered elsewhere, or represented with reverse arrows?
  3. Which field supplies “Interface Name” and which supplies the displayed “MOTS ID”?
  4. Should notes containing “expired” or “not in scope” exclude rows from topology?
  5. How should blank location, direction, target protocol, or future port be represented?
  6. Are exact duplicates suppressed with a reported warning, or rendered independently?
  7. What exact fields populate the application infrastructure box?
  8. Which standard boxes vary by operating system, cloud, site, or template variant?
  9. Should official interface data be frozen in a new snapshot schema or in a topology-specific immutable capture?
  10. What per-page interface capacity and overflow behavior are acceptable?

13. Recommended First Implementation Step

Begin with Phase 0 only: reconcile migration 0020 with the ORM/repository and restore a green topology test baseline while keeping generation fail-closed. Then implement a pure, synthetic-tested InterfaceTopologyProjection without changing production routes or databases.

This isolates the mapping rules from rendering and establishes trustworthy regression evidence before user-visible behavior changes.
