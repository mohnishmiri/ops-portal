# Session Handoff — September 25, 2026

## 1. What Was Built

This session implemented **Option B** of the multi-tab master template pipeline: using the architect's original five-tab draw.io master template directly in the topology generation workflow. Instead of requiring users to upload a pre-annotated template, the pipeline now loads a bundled copy of the architect's template from disk, extracts the correct tab based on the user's variant selection, and fills it with application data.

### Before This Session

- The pipeline required the user to upload a pre-annotated "dev template" (a manually modified single-tab .drawio file with `haf-role` attributes)
- Only one variant existed: `OUTPOST_V1`
- The dev template was missing 34 standard sections that the architect's master template contained (VPCE, Internet, AWS Tier 2, etc.)
- No way to select load balancer variant or HA/DR topology

### After This Session

- The architect's 5-tab master template (`AWS_Outpost_Topology_Template_1-v1.7.drawio`) is copied into the codebase at `src/migration_intake/topology/config/templates/outpost_v1.7.drawio`
- All four usable tabs are annotated with `haf-role` attributes (49+ roles per tab)
- Four new per-variant profiles exist (`outpost_v1_basic.json`, `_tlgw.json`, `_f5.json`, `_hadr.json`)
- A new UI card ("Generate from Standard Template") lets users select a variant and generate without uploading anything
- The legacy upload flow is completely preserved and still works
- 122 new tests were added (total topology tests: 673, up from 563)

### 2.2 The Flow (New Standard Template Path)

```
User selects variant on topology page (Card 3)
  |
  v
POST /topology/generate-standard  (variant="basic"|"tlgw"|"f5"|"hadr")
  |
  v
topology.py route handler
  -> topology_service.generate_from_standard_template(intake_id, variant, actor)
      |
      v
  load_bundled_template(variant)                   # template_loader.py
    -> reads config/templates/outpost_v1.7.drawio
    -> extract_tab(tab_name=<variant's tab>)
    -> returns single-tab XML bytes with haf-role annotations
      |
      v
  _generate_diagram(session, intake_id, template_bytes, ..., variant=variant)
    -> _is_haf_template() detects haf-roles -> True
    -> _generate_haf_diagram(variant=variant)
        -> profile_id = variant_profile_map[variant]
        -> generate_haf_topology(session, intake_id, profile_id, template_bytes)
            -> extract_topology_data() from DB
            -> fill_haf_template() with tokens, interfaces, details
      |
      v
  Stores generated .drawio and gap report as artifacts
  Creates generation run record
  Redirects to /topology/runs/{run_id}
```

## 4. Critical Bug — Must Fix Before UI Testing

### FK Violation in `generate_from_standard_template`

**Severity: BLOCKER for standard template generation from the UI.**

The `generate_from_standard_template()` service method creates a generation run with a synthetic `base_artifact_id` (a freshly-minted UUID) but **never inserts a corresponding row into the `topo_base` table**. The `gen_runs.base_artifact_id` column has a foreign key constraint `fk_gnrn_bas` pointing to `topo_base.id` with `nullable=False`.

**What will happen:** When a user clicks "Generate from template" in the UI, the database will raise an `IntegrityError` (FK violation) at `session.flush()` time, the run will fail, and the user will see a 500 error or a FAILED run.

**Location:** `src/migration_intake/application/services/topology_generation.py`, lines 456-458:

```python
# Create a synthetic base artifact record for traceability
base_id = str(uuid.uuid4())
template_sha256 = hashlib.sha256(template_bytes).hexdigest()
```

The comment says "synthetic base artifact record" but no record is actually created in `topo_base`.

**Fix needed:** Before `create_generation_run()`, insert a real `topo_base` row:

```python
topology_repo.create_base_artifact(
    artifact_id=base_id,
    intake_id=intake_id,
    filename=f"bundled_outpost_v1.7_{variant}.drawio",
    variant=variant,
    mime_type="application/vnd.jgraph.mxfile+xml",
    size_bytes=len(template_bytes),
    sha256_hex=template_sha256,
    content_address=None,  # or store via _store_content
    uploaded_at=now,
    review_state="APPROVED",  # bundled templates are pre-approved
)
```

Check `topology_repo.create_base_artifact()` for exact parameter names — the repo method wraps a `TopologyBaseArtifact` insertion. The `content_address` could be `None` if the content is on disk (bundled template), or the template bytes could be stored in the filesystem store for consistency.

**Why tests pass today:** The unit/E2E tests call `fill_haf_template()` directly, bypassing the service layer and database entirely. The service method is only exercised through the web route, which has not been tested end-to-end with a real database.

## 5. Known Gap — Token Replacement Does Not Work Against Master Template

### Problem

The placeholder binding patterns in the profiles were designed for the **old dev template** which had text like `NEEDS-CIDR`, `UNRESOLVED-subnet`, `NEEDS-AZ`. The master template uses **different descriptive placeholder text**:

| Profile Pattern | Dev Template Text | Master Template Text |
|----------------|-------------------|---------------------|
| `NEEDS-OUTPOST-ID` | `NEEDS-OUTPOST-ID` | `AT&T - AWS <Data Center Name> <Outpost Instance-Logical Id>` |
| `NEEDS-CIDR` | `NEEDS-CIDR` | `Ex: <130.x.x.x/28>` |
| `UNRESOLVED-subnet` | `UNRESOLVED-subnet` | `Private Application Subnet Ex: ...` |
| `NEEDS-AZ` | `NEEDS-AZ` | (zone text within VPC label) |
| `ACC-...-UNRESOLVED` | `ACC-PROD-MOTS-...-UNRESOLVED` | `ACC-PROD-MOTS ID-App Name` |

**What works today:** Interface population (ATT Internal grouped rendering, AWS Tier 1 grouped rendering, Azure slot filling), detail block filling, static section preservation. These all work because they target cells by `haf-role`, not by text pattern matching.

**What does NOT work:** Token replacement (outpost ID, CIDR, subnet name, security group names, account ID, availability zone). The pipeline's `_resolve_placeholder_tokens()` function searches for the pattern string inside the cell's HTML value and replaces it. Since the master template's text doesn't contain `NEEDS-CIDR` literally, the replacement is silently skipped.

**Fix needed:** Update the `pattern` / `pattern_regex` fields in each of the four new profile JSON files to match the actual text in the master template. For example:

```json
{
  "haf_role": "private_application_subnet",
  "pattern": "Ex: <130.x.x.x/28>",
  "token": "subnet_cidr",
  "required": true
}
```

Or use `pattern_regex` to match the HTML-encoded placeholder text. Inspect each cell's actual `.get("value")` in the annotated template to find the exact strings.

## 8. How the Annotation Was Done

Each tab's cells were annotated with `haf-role` XML attributes by Python scripts that:

1. Parsed the master template XML with `xml.etree.ElementTree`
2. Found cells by **cell ID** (each tab has unique IDs)
3. Added `haf-role="<role_name>"` to the matching `<mxCell>` element
4. Wrote the modified XML back to `config/templates/outpost_v1.7.drawio`

The annotation is **baked into the committed file**. The annotation scripts were run interactively and are not committed as standalone scripts, but the process is reproducible: identify cells by their value text and geometry, map them to `haf-role` names, and set the attribute.

For Tab 3 (HA/DR), Region 2 roles use the prefix `r2_` (e.g., `r2_header_line`, `r2_workload_vpc`, `r2_att_internal_in_slot`). The profile `outpost_v1_hadr.json` has corresponding `r2_` interface regions and detail blocks so that Region 2 gets filled with the same application data as Region 1.

## 9. Design Decisions Worth Knowing

| Decision | Rationale |
|----------|-----------|
| Annotated copy in `config/templates/` | The original template in `docs/` is never modified. The copy in `config/templates/` is the pipeline's working file. |
| Cell IDs differ between tabs | Each tab has completely independent cell IDs. Annotations were done per-tab by matching cell text values and geometry, not by ID. |
| `variant=None` maps to `OUTPOST_V1` | Backward compatibility. Existing uploads use the original dev template + `OUTPOST_V1` profile. |
| HA/DR fills both regions identically | The plan says to fill both outpost regions with the same app data. The pipeline doesn't yet have per-region data sourcing. |
| No DB migration needed | No schema changes. The `variant` column already existed on `topo_base`. |
| AWS Tier 1 color fix already in place | The connector style in `aws_tier1_generator.py` already uses `{color}` template variable. No fix was needed. |
| Profiles copy placeholder bindings from `OUTPOST_V1` | All four new profiles use the same binding patterns as the original, which don't match the master template's text (see Section 5). |
